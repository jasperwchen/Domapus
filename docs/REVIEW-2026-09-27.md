# End-to-end review, 2026-09-27

Keep the static architecture. Computing housing statistics once during publication,
then serving small color files separately from detailed records, is the right design
for this product. The biggest opportunities are consistent releases, reliable failure
states, accessible controls, and measurements that track what the user actually sees.
A backend, another state library, or a replacement map engine would add complexity
without addressing the main findings.

This review covers acquisition, ingestion, calendar arithmetic, statistics, encoding,
publication workflows, browser loading, map rendering, ZIP details, mobile interaction,
and PNG/PDF export. It includes source inspection, isolated pipeline reproductions,
Chrome checks at 1440×900 and 375×812, and normal PNG/PDF downloads. These are local
checks against the committed August release, not observations of a failed live deploy.

All 15 findings and the concrete build/route/script improvements were implemented
and locally verified on September 28. The numbered findings below preserve the original
review evidence; they describe the pre-fix behavior.

Release identity now covers history and statistical metadata, archives are immutable
and verified, and the browser checks related files against a shared release ID.
Exports fail explicitly and offer retries, captures keep one configuration, and detail
loading failures remain visible without hiding a working map. Calendar validation,
local inputs, chart fallback, coordinate validation, mobile gestures, focus handling,
and render-completion timing are corrected. Forecast evaluation uses origin-specific
tiers with a 12-month separation from calibration. The map route is lazy and the build
copies only deployable assets. Unsupported local deployment scripts were removed.

Verification: 83 Python tests, 187 frontend tests, and the Node build-staging test pass;
TypeScript/build and all six workflow checks pass. Lint has no errors and four existing
warnings. Chrome checks passed for PNG/PDF downloads, frozen export settings, state
selection, modal focus containment/restoration, map/detail failure retries, invalid
coordinates, and mobile dates and sheet controls. A 1.8-second delayed color request
measured 1.93 seconds through rendering; methodology made no map-data requests.
The final measured Vite build took 6.52 seconds, with public-file staging at 3.4 seconds;
these local disk timings are not a controlled speed benchmark.

Visual verification also caught a stylesheet-order conflict introduced by lazy loading:
MapLibre's positioning rule collapsed the main export container. Explicit positioning
fixes it, and Chrome now checks canvas dimensions and aspect ratios for national and
state exports. Regenerated PNG and preview images were visually inspected.

The corrected backtest on the existing local panel used 80 origins (41 calibration,
39 evaluation, three excluded for overlap) and 25,819 eligible ZIPs. Its 12-month
empirical coverage was 87.03% for the 80% target; model error remained below the
no-change baseline at each horizon. These measurements do not replace the published
release's statistics until a data rebuild.

Evidence is retained in ignored `build/review-2026-09-28/`. Python used the installed
3.13.5 interpreter. No production data or deployment was changed. Immutable release
paths and the corrected forecast statistics take effect on the next data rebuild.

## Fix first: releases must describe all the data they publish

### 1. P1: Corrections to history or forecast bands can be skipped

The release identifier decides whether a completed pipeline run gets committed and
deployed. It hashes the current snapshot and color files, but excludes historical
series, the history index, forecast interval multipliers, and manifest-only diagnostics.
Changing those excluded outputs while leaving current values and colors unchanged
produces the same identifier. The workflow can then skip the corrected history archive,
commit, and deploy. A changed upstream fingerprint also remains uncommitted on this
path, which can cause later scheduled runs to repeat the same expensive work.

Evidence: `release_digest` accepts only the snapshot digest and paint assets;
the workflow uses `content_changed` for both archival and publication decisions.
This is a verified dependency gap, not a claim that the current public charts are wrong.

Include every user-visible output in a deterministic release inventory. Hash history
files as they are written, include the index and relevant metadata, and exclude only
run-specific timestamps. Track probe state separately if it should advance without a
new public release. Test a history-only correction and an interval-only correction.

Sources: [release identity](../pipeline/serialize.py),
[publication gates](../.github/workflows/update_data.yml).

### 2. P1: The same history archive name can refer to different releases

History archives supply the chart files that are intentionally absent from Git.
Their names contain only the data period. A same-month rebuild overwrites the archive
before the data commit is pushed. If that push fails, or another branch rebuilds the
same period, a subsequent deploy can combine the existing snapshot with different
history. Deploy selects the archive by period and does not verify a content digest.
The snapshot archive has the opposite problem: an existing same-period file is skipped,
so it can remain the first revision while the site serves a later one.

Name archives by release identifier and verify their hashes during deployment.
Publish immutable assets before committing their references. This makes failed pushes
leave harmless unreferenced assets and makes rollbacks reproducible. Test two revisions
of one month and a failed push between archival and publication.

Sources: [archive upload](../.github/workflows/update_data.yml),
[history retrieval](../.github/workflows/deploy.yml).

### 3. P2: A browser can combine individually valid files from different releases

The build embeds color filenames so the map can load quickly. The browser separately
fetches the manifest and snapshot. Color validation checks length and class count,
which cannot establish that all three describe the same release. The history loader
also caches its date index for the session but retrieves additional buckets later
through stable filenames. A page left open across deployment can combine an old date
axis with new values.

Carry one release identifier through the page, manifest, snapshot, and history index.
Use versioned history paths and check identities before joining data. Preserve parallel
color loading. Test an old page with new manifest responses and an old history index
with a new bucket. This needs neither a server nor main-thread hashing of large files.

Sources: [inline filenames](../vite.config.ts),
[dashboard loading](../src/components/dashboard/HousingDashboard.tsx),
[color validation](../src/lib/paint-table.ts), [history cache](../src/lib/history.ts).

## Data ingestion and statistical correctness

### 4. P2: Explicit local input can be ignored

Local CSV arguments are meant to reproduce or inspect a particular input. The driver
checks remote fingerprints and returns early before considering those arguments.
With matching fingerprints, a supplied local Redfin file never reaches ingestion.
The isolated reproduction returned success with `ingest_called: false`.

Only take the unchanged-upstream shortcut when no local inputs were supplied.
Retain the existing rule that local files must not inherit upstream fingerprints.
Add a matching-fingerprint test for each local-input argument.

Source: [driver's probe and acquisition stages](../pipeline/__main__.py).

### 5. P2: Missing months silently change the meaning of annual changes

Annual changes and monthly forecasts depend on calendar spacing. Redfin changes use
the twelfth preceding position; Zillow uses `date_cols[-13]`. Panel validation requires
sorted, unique periods but does not require consecutive months. An omitted month can
therefore turn a twelve-month comparison into a thirteen-month comparison.

A synthetic series ending September 2026 with October 2025 omitted passed panel
validation. Zillow's calculation used August 2025 instead of September 2025 and
reported 109.09% instead of 91.67%. This reproduces a handling defect, not a gap found
in the current upstream feed.

Validate calendar continuity at ingestion or align to an explicit monthly axis with
null gaps. Calculate annual comparisons by calendar key. Define how the forecast
handles missing periods before applying consecutive log differences.

Sources: [changes](../pipeline/changes.py), [Zillow processing](../pipeline/zhvi.py),
[panel validation](../pipeline/panel.py), [forecast input](../pipeline/forecast.py).

### 6. P2: Forecast evaluation does not fully reproduce the production rule

The production forecast uses each ZIP's observation count to choose its shrinkage
behavior. Backtest folds call `fit` without those counts, and eligibility is based on
the full panel rather than what was available at each historical origin. In addition,
the calibration and evaluation origins are adjacent quarterly origins: the last
twelve-month calibration outcome occurs after the first evaluation origin. The
interval calibration therefore uses information unavailable at that first origin.

Use observation counts and eligibility as of each fold. Leave a twelve-month gap
between the last calibration origin and first evaluation origin, or use rolling
calibration restricted to outcomes already observed. Compare results by history tier
and horizon. This is an evaluation improvement, not evidence that a more complex model
would be better. The published error ratios currently beat the unchanged-level baseline.

The chart also describes the selected band percentage as achieved backtest coverage.
The published nominal 80% band covers about 87.9% of twelve-month evaluation outcomes.
Label the selection as its target coverage and distinguish measured coverage when shown.

Sources: [fit and backtest](../pipeline/forecast.py),
[forecast caption](../src/components/dashboard/Sparkline.tsx),
[published diagnostics](../public/data/manifest.json).

## Browser presentation and interaction

### 7. P2: Partial loading failures hide the explanation and recovery path

The small color files let the map remain useful when the detailed snapshot fails.
However, the dashboard displays its loading error only when it also lacks a color
table. With a successful color request and a snapshot returning HTTP 503, the browser
showed a colored map but no explanation for unavailable search and ZIP details.
The export panel could also open without usable detailed data.

Show a nonblocking message beside the affected controls and provide a retry for the
failed resource. Represent map colors, ZIP details, history, and export readiness
separately. The initial snapshot prefetch also needs a timeout: awaiting it precedes
the worker request timeout and can otherwise leave details waiting indefinitely.

Sources: [dashboard error gate](../src/components/dashboard/HousingDashboard.tsx),
[worker lifecycle](../src/hooks/useDataWorker.ts), [prefetch](../index.html).

### 8. P2: An invalid shared map position leaves an endless loading screen

URL coordinates restore a shared view, but numeric parsing does not validate latitude
against map bounds. Opening `?lat=999&lng=0&zoom=6` reproduced a page with no map and a
persistent loading message. The map constructor failure is logged without a useful
initialization error state.

Validate coordinates and zoom before construction, fall back to the default view for
invalid parameters, and surface genuine initialization failures with a retry.

Source: [map initialization](../src/components/dashboard/MapLibreMap.tsx).

### 9. P2: One missing chart series makes other valid series unreachable

The history chart initially selects Zillow's typical value and retains that selection
when the ZIP changes. If the selected series has no usable geometry, the chart returns
its empty message before rendering the series buttons. A ZIP can have sale-price and
sales-count history that the reader cannot select.

Choose a usable series when the ZIP changes, or keep the series controls visible above
the empty state. Test a Redfin-only ZIP and navigation between ZIPs with different
series. Availability should mean usable observations, not just the existence of an array.

Browser reproduction: removing only Zillow history from a valid ZIP response left
sale-price observations present, but displayed the empty message and zero sale-price
selection buttons.

Source: [chart selection and early return](../src/components/dashboard/Sparkline.tsx).

### 10. P2: The export dialog does not contain keyboard focus

The export dialog declares itself modal but neither moves focus inside nor traps it.
In Chrome, opening it left focus on the body; tabbing eventually reached Methodology
and other controls behind the dialog. The mobile detail sheet also lacks equivalent
dialog/focus behavior and a keyboard control for expanding the sheet. The phone's
icon-only export button has no accessible name.

Use one established dialog primitive for modal focus, Escape, background inertness,
and returning focus to the opener. Give icon buttons explicit names. Keep sheet drag
behavior separate from dialog semantics and provide an expand/collapse button.
These behaviors follow the [WAI modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/).

Sources: [export dialog](../src/components/dashboard/export/ExportSidebar.tsx),
[mobile sheet](../src/components/dashboard/MobileBottomSheet.tsx),
[export trigger](../src/components/MapExport.tsx).

### 11. P2: Slow sheet drags can be treated as fast flings

The mobile sheet chooses its final position using a velocity calculation. Its distance
covers the whole gesture, while its elapsed time covers only the interval since the
last pointer move. For example, a 100-pixel drag lasting one second, released ten
milliseconds after the last move, is treated as 10 pixels/ms rather than 0.1 pixels/ms.

Measure distance and time over the same recent sample interval, including a stationary
release. Test slow drags, fast flicks, and a drag followed by a pause. Removing the
unused `startTime` field in this cleanup does not fix or change this existing behavior.

Source: [pointer release](../src/components/dashboard/MobileBottomSheet.tsx).

### 12. P2: Data dates disappear where screen space is smallest

The phone layout fits 375 pixels without horizontal overflow, but the header's source
periods are hidden below the extra-large breakpoint. A reader can see a prominent
housing value without a nearby date; naming it a monthly index does not establish
which month it describes. Map buttons measured 29×29 pixels, which also makes touch
interaction less forgiving.

Put the selected metric's period next to the legend or value on every screen size.
Offer the full source window in a compact details disclosure. Enlarge touch hit areas
without enlarging every icon. The existing restrained visual hierarchy and shared
color scale should remain.

Sources: [header dates](../src/components/dashboard/TopBar.tsx),
[ZIP details](../src/components/dashboard/Sidebar.tsx).

## Export reliability

### 13. P2: Export readiness can mean failure, incomplete tiles, or endless waiting

The export builds separate maps for the mainland and insets. After a map's load event,
a ten-second fallback counts it as ready even if tiles are still incomplete. An error
while adding its layers also increments the ready count. Conversely, failure to load
the initial basemap style occurs before this fallback is installed, leaving the panel
on “Rendering...” indefinitely.

A browser check returning HTTP 503 for the export style request left the export
button disabled on “Rendering...” after twelve seconds.

Capture has another gap: it clears its timeout before awaiting the final render event.
If that render never occurs, capture never settles. Alaska and Hawaii capture failures
are swallowed, allowing a national download to omit an expected inset silently.

Use explicit pending/ready/failed states for each requested map. Keep the timeout active
until the canvas is captured, clean up listeners on every outcome, and report failures
with retry. A requested inset should either be present or produce a visible decision
before export. Exercise style failure, slow tiles, missing final render, and failed insets.

Source: [readiness and canvas capture](../src/components/dashboard/export/PrintStage.tsx).

### 14. P2: Export settings can change while an image is being captured

Most layout and region controls remain enabled during export. The capture awaits map
canvases, then reads current layout and label refs. A setting change during that wait
can produce a file whose captured map, labels, and filename describe different settings.

Snapshot the full export configuration at click time and keep its map instances alive
until completion, or disable configuration controls for the capture. Test a delayed
capture with region, title, and legend changes. The existing shared preview/canvas
layout is useful and should be retained.

Sources: [export controls](../src/components/dashboard/export/ExportSidebar.tsx),
[post-capture configuration reads](../src/components/dashboard/export/PrintStage.tsx).

## Performance and architectural simplification

### 15. P2: The metric-switch timer stops before the requested data necessarily arrives

The metric-switch measurement ends after two animation frames following a selection
change. It does not await the selected color file or the painter's completion. It can
therefore report a fast switch while the map still shows the old metric. Likewise,
`hasPainted` is set when work is scheduled rather than after that work is displayed.

Measure selection to first rendered frame with the requested color source. Keep
separate network and painting timings if useful, and associate them with a request
identifier so superseded switches cannot finish the wrong measurement. Retain the
existing source-reload tripwire; it checks a real map operation.

A browser check delayed the new color request by 2.2 seconds. The request took
2,216 ms, while `map:metricSwitch` reported 22.6 ms.

Source: [paint scheduling and timing](../src/components/dashboard/MapLibreMap.tsx).

Measured costs and practical next steps:

| Area | Evidence | Recommendation |
|---|---|---|
| Initial map | Color response about 27.6 KB; detailed snapshot about 2.67 MB in the local browser | Preserve independent color loading and off-main-thread snapshot processing. |
| JavaScript | Production main bundle about 140.6 KB gzip; MapLibre about 278.1 KB gzip, plus its worker | The map engine is the major library cost. Avoid replacement or aggressive chunking without a measured benefit. |
| Methodology route | The map route is eagerly imported even though methodology is lazy | Lazy-load the map route too, and avoid starting map-only prefetches on a direct methodology visit. |
| Export | Export chunk about 143.9 KB gzip; canvas is 3600×2700 | Keep it lazy. Profile peak browser memory for national PDF export before raising resolution or adding more maps. |
| Pipeline statistics | Cached-panel runs: noise 7.59 s, forecast 5.07 s, spatial 1.88 s | Profile ingestion and history writing before optimizing these already vectorized stages. These are local component timings, not full-run totals. |
| Build copying | Output-directory preparation took 10.6 of 13.4 s in the final Vite build; pruning then removed 20.9 MB | Stage only deployable public assets instead of copying inputs and archives and deleting them afterward. Measure disk I/O before changing the build. |

Output preparation also copies thousands of required history files. The timing does
not establish how much would be saved by excluding the 20.9 MB that is later pruned.

The largest components combine map lifecycle, data loading, view state, and rendering.
Separate those responsibilities only while fixing their ownership problems. A small
loader state model and one export lifecycle would remove more complexity than splitting
files by line count. Keep the single palette, shared classification rules, typed column
storage, lazy chart/export modules, and pipeline-to-frontend golden fixtures.

One stale developer command remains: `npm run deploy` calls `gh-pages`, which is neither
declared nor installed. Prefer removing that unsupported script and documenting the
existing deployment workflow, unless local deployment is intentionally supported.

## Cleanup performed and verification

Removed unused CSS color families, an obsolete eight-stop palette, unused animation
and containment utilities, a test-only map selector, an unused focus class, and a
`font-display` declaration placed on `body`, where it has no effect. Removed the

An import-graph scan found no other unreachable application module except the
intentionally retained sponsor banner. Its commented mount, deferred reliability
features, generated color code, and committed geometry asset remain intact. No
production data was regenerated or published, and existing user edits were preserved.

After cleanup: **79 Python tests and 162 frontend tests pass**, TypeScript and the
production build pass, and frontend/config lint has **0 errors and the same 4 existing
warnings**. The previous frontend total was 163 because it included the deleted unused
method's test. The baseline workflow validation also passed. Python verification used
the installed 3.13.5 interpreter rather than CI's 3.14; dependencies were not changed.

Normal browser checks produced both PNG and PDF downloads and exercised a regional
color scale. Browser fault checks reproduced the silent snapshot failure, invalid
latitude, and keyboard-focus escape. Local diagnostic scripts, JSON results,
screenshots, and downloads are retained in `build/review-2026-09-27/`, which is ignored.
Local history files were older than the committed snapshot during this review; that
local mismatch is not evidence of a production mismatch.

Recommended implementation order: complete release identity and immutable archives;
then export and loading failures; then calendar/input correctness and chart selection;
then accessibility and mobile interaction; then performance instrumentation and measured
optimizations. Re-evaluate forecast calibration before changing the forecast model.
